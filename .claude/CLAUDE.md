# Claude Code Agent Instructions

## 絶対ルール

1. **各フェーズで指定されたSubagentに委譲すること。自分で実行してはいけない。**
2. エラーは最大3回、別アプローチで自律修復する
3. 各フェーズ完了時にファイルを出力する（SPEC.md / DESIGN.md / PLAN.md / DONE.md）
4. 実装前にSPEC.mdを必ず参照する（仕様ドリフト禁止）

---

## フェーズ定義と必須委譲先

### Phase 0: 仕様固め（メインエージェントが直接実行）

ユーザーから要求を受け取ったら、**SPEC.mdを生成する前に**以下のカテゴリを順番に質問して暗黙要件を洗い出す。
ユーザーが「もういい」と言うまで、または全カテゴリを聞き終えるまで質問を続ける。

#### 洗い出しチェックリスト（必ず全カテゴリ確認すること）

**① ユーザーとユースケース**
- 誰が使うか（エンドユーザー像、技術レベル）
- どんな場面で使うか（頻度・デバイス・オフライン要否）
- 一番やりたいことは何か（コアユースケースを1つ挙げるとしたら？）

**② 機能の境界**
- やらなくていいこと（スコープ外）は何か
- 今回不要でフェーズ2以降に回せる機能はあるか
- 既存システムとの連携は必要か

**③ データと状態**
- 扱うデータの種類・量・更新頻度
- データの永続化が必要か（ローカル / DB / クラウド）
- 複数ユーザー間でデータを共有するか

**④ 非機能要件（NFRs）**
- 応答速度の許容範囲（「遅くてもいい」か「リアルタイム必須」か）
- 同時利用者数の想定
- セキュリティ要件（認証・認可・データ暗号化）
- 障害時の許容ダウンタイム

**⑤ 制約**
- 使用禁止の技術・ライブラリはあるか
- デプロイ先の制約（クラウド指定 / オンプレ / ローカルのみ）
- 予算・コスト上限（APIコスト、インフラコスト）
- 期限はあるか

**⑥ 完了の定義**
- 「完成した」と判断する基準は何か
- 受け入れテストのシナリオを1つ挙げるとしたら？

#### 洗い出し後の作業

全カテゴリ確認後、SPEC.mdを生成してユーザーに確認を求める。
「この仕様で進めますか？修正があれば教えてください」と聞き、OKが出たらコミットしてPhase 1へ。

- git管理されていなければ: `.gitignore`生成 → `git init` → `git add SPEC.md` → `git commit -m "docs: SPEC.md初稿"`

### Phase 1: 技術設計（**architectに委譲すること。自分で設計してはいけない。**）

1. **architectサブエージェントを起動**してDESIGN.mdを生成させる
2. **reviewerサブエージェントを起動**してDESIGN.mdをレビューさせる
3. レビュー結果が「要修正」の場合: architectに修正させる（最大3回）
4. 「LGTM」取得後: `git add DESIGN.md` → `git commit -m "docs: DESIGN.md"`

### Phase 2: 実装計画（**plannerに委譲すること。architectは使わない。**）

1. **plannerサブエージェントを起動**してPLAN.mdを生成させる
2. **reviewerサブエージェントを起動**してPLAN.mdをレビューさせる
3. 「LGTM」取得後: `git add PLAN.md` → `git commit -m "docs: PLAN.md"`

### Phase 3: 実装（**implementerに委譲すること。タスクごとに1回ずつ起動。**）

PLAN.mdの各タスクに対して:
1. **implementerサブエージェントを起動**して1タスクを実装させる
2. implementerから「実装完了」サマリーを受け取る
3. `git commit` する（削除ファイルがある場合は明示指定、新規追加のみなら `git add <dir>` 可）
4. 次のタスクへ進む

コミットメッセージプレフィックス: `feat:` / `fix:` / `chore:`

### Phase 4: 統合テスト（**testerに委譲すること。**）

1. **testerサブエージェントを起動**してテストを実行させる
2. 「PASS」の場合: Phase 5へ進む
3. 「FAIL」の場合:
   - **debuggerサブエージェントを起動**してFIX-PLAN.mdを生成させる
   - Phase 3（修正実装）→ Phase 4（再テスト）のループ（最大2回）

### Phase 5: 完了レポート（メインエージェントが直接実行）

- DONE.mdを生成する（達成率・未達項目・理由を記録）
- 未達があっても理由を明記すれば完了とする
- `git add DONE.md` → `git commit -m "docs: DONE.md 完了レポート"`

---

## エラー処理

- エラーが発生したらerror.logに記録する
- 修復を3回試みても解決しない場合はerror.logに詳細を残してDONE.mdを生成する

---

## コミット規約

- `git add -A` 禁止。削除ファイルがある場合は明示指定
- 新規追加のみの場合は `git add <ディレクトリ>` または `git add <ファイル>` を使う
- メッセージプレフィックス: `feat:` / `fix:` / `docs:` / `chore:`
